# Brink — Design Decisions & Session Record

> Living design doc for `claude-brink` — the project's durable engineering record, written as the decisions were made. Created during a design session on 2026-06-24/25.
>
> *Commit hashes below refer to the pre-release private development history and do not resolve in this repository; v1.0.0 is published as a single commit.*

## Summary

A Claude Code **plugin** that gracefully **auto-pauses** the agent before it hits a usage limit (writes `HANDOFF.md` and stops), **notifies** you on the desktop, and **optionally auto-resumes** the work when the window resets.

## Locked decisions (with why)

1. **Core identity = auto-pause + handoff.** The notifier space is saturated; the graceful self-pause-with-handoff middle is empty. This is the differentiator and the headline.
2. **Platform = B** (cross-platform via HTTP push + Windows-first native toast). HTTP push (ntfy/Pushover) is one line that works on every OS and reaches the phone, with zero untested OS code. Native desktop toast ships Windows-first; mac/Linux documented. The whole field skews ~80% macOS-only — cross-platform is the open lane.
3. **Packaging = Claude Code plugin** (not a bare skill). A skill (SKILL.md) can't install hooks; a plugin bundles hooks + command for one-command install — the convenience moat. **CORRECTION (verified 2026-06-30 vs official plugin docs): a plugin CANNOT register the top-level `statusLine`.** A plugin's bundled `settings.json` honors only `agent` + `subagentStatusLine`, and there is no `statusLine` field in `plugin.json`. Since the statusLine IS Brink's sensor (the only thing that sees `rate_limits` and writes `state.json`), the install story is: **plugin auto-wires the hooks via `hooks/hooks.json`; the statusLine is added separately** — by `node src/install.js --statusline` (the `brink init` path, which CAN write it) or one documented manual line in the user's `~/.claude/settings.json`. The "one-command install" is therefore hooks-complete but needs one extra step for the sensor. (This is a Claude-Code platform limit, not a Brink bug; document it honestly.)
4. **Name = Brink / `claude-brink`.** Verified clean: free on npm + 0 GitHub results. Fits ("stops Claude at the brink before it goes over"). Rejected for in-niche name collisions: **Headroom** (allandecastro/headroom), **Pitstop** (Livin21/pitstop ★7, pitstop-for-claude), **Baton** (bakabaka91/claude-baton ★25), **Siesta** (siestadeck), **Guardrail** (639 hits). Refuel/Yield/Coast were clear runner-ups.
5. **Thresholds (defaults, all user-configurable):** 5h — warn 75/85, **pause ~93%** (lower than the wall so the handoff itself fits). Weekly — warn 80/90, **pause ~95%** (weekly overshoot costs *days*, so it gets the earlier/safer alarm; counter to the first instinct of a higher weekly threshold).
7. **Reset ping ("budget's back") = weekly ON, 5h OFF by default (both toggleable), gated by a floor (2026-06-30).** A 5h window resets several times a day, including overnight — a "fresh 5h" buzz that frequent trains you to ignore notifications, which erodes the approaching-limit pings that matter; so 5h is off by default. The weekly reset is *days* of budget returning, genuinely worth announcing → on by default. **Floor gate:** a reset only pings if you were at/above the floor (default 80% weekly / 75% 5h) before it rolled — a window resetting from 12% isn't budget you were waiting on, so it stays silent. Detection signal = `resets_at` epoch jumping forward (a real rollover jumps it by hours/days; a 60s guard kills float jitter); naturally debounced because the statusline writes the new epoch after firing.
6. **Resume = external, opt-in, Windows Task Scheduler in v1.** A paused Claude can't wake itself; resume must be external. Self-contained one-shot scheduled task (no third-party dependency, no CLI-output screen-scraping) reading the authoritative `resets_at`. mac/Linux = launchd/cron documented. Never marketed as native.

## What we verified (facts)

- **Only the statusLine** receives live usage on stdin: `rate_limits.five_hour.used_percentage` / `.resets_at` (epoch **seconds**) + `seven_day`. **Hooks do NOT** get `rate_limits` — hence the **state-file bridge** (statusLine writes a small JSON each refresh; the hook reads it).
- **`PreToolUse` deny physically blocks** the tool (not "asked to stop"). `permissionDecisionReason` + `additionalContext` are fed to the **model**, so the wind-down instruction is actually read. `systemMessage`/top-level `reason` are user-only.
- **No native usage-threshold hook** exists. The `Notification` hook fires on permission/idle/auth only. `StopFailure` matcher `rate_limit` fires only *after* the wall.
- **No native auto-resume** (`--auto-resume`/`--wait`); confirmed via open issues (#62788 etc.). `claude --resume <id> -p "…"` spawns a fresh process.
- **ccusage is an approximation** — it hour-rounds the 5h block (observed: it reported reset ~30 min off the real `resets_at` shown in the live UI). The plugin must read the statusLine `resets_at`, not ccusage. (ccusage is only useful as an off-disk/idle poller.)
- **This machine already has** a statusLine reading the 5h/7d % and working Windows toast hooks (AppId `Claude.Code`) — fast early wins for Phases 1–2.
- **`bypassPermissions` is on** in this user's config — must test that an explicit `PreToolUse` deny still overrides it before shipping.
- **`jq` is NOT installed** on this machine (checked PATH + scoop/choco/winget/git locations). The user's existing `jq`-based `statusline-command.sh` is therefore **failing silently** (Claude Code swallows statusline errors). → **Runtime decision (locked): Node.js** (v24 present): `JSON.parse` is built in, zero external deps, cross-platform — matches Option B. All Brink logic is Node; PowerShell is used only for the Windows-specific toast + Task-Scheduler resume leaves. Phase 1 (`src/statusline-brink.js`) built + tested via `tests/run.js` (3 cases pass).

## Positioning / prior art

Closest competitors and what they miss: **code-notify** (cross-platform, both windows, pings on reset — but not a plugin, no ntfy/Pushover, no countdown); **jens-duttke/usage-monitor-for-claude** (Windows-native, advanced — but not a plugin, phone push is DIY); **claude-notifications-go** (real CC plugin with ntfy/Pushover plumbing — but event-driven, not usage-threshold). **Claude Meter** launched ~2026-06-24 with a similar "stop getting surprised by rate limits" pitch, as a *menu-bar app*. The CC-native plugin + auto-pause combo is still unoccupied.

One-liner: *"The first Claude-Code-native plugin that pauses your agent cleanly before the wall, hands off, and picks back up when your quota resets."*

Marketing vocabulary harvested from X (verbatim pain language): *hit my limit · usage anxiety · before reset · rolling session · daily/weekly window · surprised by rate limits · before your flow gets interrupted · rate limit hit.*

## Cross-CLI architecture (decided 2026-06-25)

**Shared Node core + thin per-CLI adapters** (hybrid — NOT a standalone daemon, NOT N separate plugins). Verified across Codex/Gemini/opencode/Cline/Crush/aider/Hermes.
- **Core (portable, write once):** threshold engine, notifier fan-out (`notify.js` — done Phase 2), handoff-doc generator, resume scheduler, a headless `brink` CLI emitting usage JSON.
- **Adapter (per-CLI, ~150 lines each):** `readUsage() -> {provider, window, used_percentage, resets_at}` + `installPauseHook(threshold)` (no-op / notify-only where the CLI can't block).
- **Auto-pause works only where the CLI has BOTH a blocking pre-tool hook AND readable usage:** Claude Code (✅ best, ship first), Gemini CLI (✅), opencode (✅), Codex (⚠️ leaky AND data-blocked — PreToolUse reliably gates Bash only; AND `rate_limits` is `null` upstream in rollout files (codex#14880), so usage can't be read today. Adapter verified vs Codex source + tested on 53 real local rollouts, but inert until OpenAI fixes the null or we add the auth.json usage-endpoint source), Hermes **Agent CLI** (⚠️ — the Hermes *model* has NO hook surface), Cline (⚠️ macOS/Linux only — no Windows), Crush (notify-only, no usage feed), aider (❌ notify-only, no hooks).
- **Public promise (honest):** "auto-pause on Claude/Gemini/opencode, notify-before-limit everywhere else, clean path to add CLIs" — NOT "auto-pause for every model."
- **Install:** `npm i -g brink` → `brink init` auto-detects installed CLIs (`~/.claude`, `~/.codex`, `~/.gemini`…) and writes each one's NATIVE config (no hand-editing). WinGet (Windows) + CC plugin-marketplace listing later. Gotchas: Codex trust-gates third-party hooks by hash; Codex `notify`/profiles ignored in project-local config (write user-level); Gemini/Cline show a security-consent prompt on install.
- **Plan impact:** keep Claude-first; introduce the adapter SEAM now (core logic behind a `ClaudeAdapter` implementing the 2-method contract) + one stubbed adapter to prove the seam; build the 2nd real adapter (Gemini cleanest) only when a real user is on it. Don't over-abstract before v1 ships.

## Architecture (the cycle)

```
Claude Code ──(usage JSON each refresh)──▶ statusLine (sensor) ──writes──▶ state.json (bus)
                                                                              │ reads
  every tool call ───────────────────────────▶ PreToolUse hook ──▶ allow / warn / PAUSE
                                                                              │
                                              notifier: ntfy/Pushover push + Windows toast
                                                                              │ (on pause)
                                          (opt) Task Scheduler @ resets_at ──▶ claude --resume
```

## Live-test findings (2026-06-26) — core PROVEN, handoff UX needs redesign

Ran a real headless `claude -p` in an isolated sandbox (its own `.claude/settings.json` with `bypassPermissions` + the Brink PreToolUse hook, fake 99% state). Results:
- ✅ **PROVEN: the deny fires and OVERRIDES `bypassPermissions`.** The Write tool was blocked, the model reported "the tool came back ... with a message claiming a 5h usage limit", and `ran.txt` was NOT created. Control run at 10% allowed normally (file created). **The #1 unknown is resolved — auto-pause is real on this machine.**
- ⚠️ **BUG 1 — self-contradictory deny.** "Do NOT call any more tools" + "write HANDOFF.md and commit" both need tools → impossible. Denying everything blocks the handoff tools too.
- ⚠️ **BUG 2 — the model distrusts the message as a prompt injection.** The nested model said *"I'm treating that message as spurious/injected rather than a genuine directive"* and refused to write the handoff. **Relying on the model to cooperate with the deny instruction is fragile.**
- ⚠️ **BUG 3 — context-blind message.** It said "commit" in a non-git dir; the model flagged the mismatch.

**Redesign (validates the council's handoff-as-spine reframe):** Brink must WRITE `HANDOFF.md` ITSELF (deterministically, from session state / the transcript), NOT instruct the model to. The deny should cleanly block + state a short, credible, non-contradictory, injection-resistant reason (e.g. "Paused by Brink at 99% of your 5h limit — resets HH:MM. Stopping here; your work is saved to HANDOFF.md."). If the model must still act, the hook has to ALLOW Write→HANDOFF.md + git commit (read `tool_name`/`tool_input` from hook stdin) and deny the rest — but Brink writing it itself is more robust. This is now Phase 5.

## Full product review + live-fire hardening (2026-07-04)

Ran a 9-agent review workflow (6 dimensions: core/adapters/Windows/security/docs/packaging + 3 black-box simulators; 24/24 sim scenarios passed) plus manual live-fire testing on the real machine. **41 findings (0 critical / 10 high / 16 med / 15 low).** The adversarial-verification phase of the workflow was itself killed by the account's 5h usage limit — the product's own thesis, demonstrated mid-review. All code-level highs fixed same day; all 6 suites green after.

**Live-fire discoveries (would never have surfaced in unit tests):**
1. **Detached PowerShell dies.** PS 5.1 cannot start under `DETACHED_PROCESS` (no console) and an attached child dies with the parent's console. So the Phase-7 arming spawn NEVER registered its task (flag said armed; nothing scheduled), and the toast leaf of notify was equally broken from the hook chain. **Fix:** arming is now SYNCHRONOUS in the pause path (~0.8s, acceptable for a terminal event; armed flag written only after the scheduler confirms, failure notifies); the toast child is non-detached + awaited inside notify.js (node survives detachment, so notify.js is the fire-and-forget layer). E2E re-verified: real task registered, fires at reset+90s to the second.
2. **`-ExecutionPolicy Bypass` was missing everywhere** — stock Windows (Restricted) would silently refuse every .ps1. Added to all PowerShell invocations incl. the scheduled task's action string.
3. **Resume self-block (worst logic bug):** a resumed headless session has no statusline, so state.json still said 99% from pause time → the resumed session's FIRST tool call got denied. Fix: stale-epoch gate — a window whose `resets_at` already passed has rolled, its pct is nulled.

**Other fixes from the review:** per-PID state tmp + guarded rename (two concurrent sessions crashed 21% of refreshes on the shared tmp — reproduced live by the sim); hook stdin `session_id` preferred over shared state (multi-window armed the wrong session); deep threshold merge (partial config override silently wiped warn bands / the other window's pause); notify.js now actually reads `config.json` (`ntfy_topic`/`windows_toast` were dead documented keys); install.js aborts on unparseable settings.json instead of wiping it (a BOM was enough) + BOM-tolerant + loud statusLine replacement; resume-once.ps1 guards a missing project dir, forwards `buffer_seconds` on weekly re-arm, and self-deletes only when no future trigger exists (re-armed chains survive); task name sanitized from Sid; trailing-backslash Proj guard (would escape the task's quoted args); honest deny when the handoff write failed; `resetText` shows the date for far (weekly) resets; flag-file GC (14d); spawn error listeners + `windowsHide` everywhere; `package.json` created (`claude-brink`, matching the README promise); config.example cleaned (dead `escape_hatch_file` + unimplemented `pushover` removed, `skip_permissions` danger documented).

**README honesty pass:** Pushover → planned; Codex "notify works today" corrected (it's null-blocked too); Crush/aider → planned (no adapters exist); "launchd/cron documented" → planned; HANDOFF examples marked illustrative; plugin-statusline instructions now warn against the versioned plugin path (silent death on update) and route through a stable clone; countdown scoped to 5h; toast scoped to Windows; `skip_permissions` risk stated.

**Deferred (tracked, not fixed):** HANDOFF.md content sanitization + integrity check before resume consumes it (prompt-injection surface — resume is off-by-default, acceptable for v1 with the warning); Codex adapter re-scans the whole sessions tree per call (inert feature today); same-privilege tamper (a prompt-injected agent could write the DISABLED hatch — document as a known boundary); multi-session per-session state files (bigger redesign; per-PID tmp removes the crash, wrong-sid removed via hook stdin); pre-publish scrub of DECISIONS/docs personal details before flipping public.

## Burn-in findings

- **2026-07-05 — the 03:10 no-show (deny reason promised a resume that was never armed).** First real overnight pause (5h window, reset 03:10): handoffs written correctly in two separate projects (00:33 and 01:47), pause + toast fired, but nothing resumed at reset. Not a scheduler failure — resume is off-by-default (locked decision) and off in the live config, so `shouldArm()` correctly never registered a task. The *expectation* mismatch came from brink.js: the deny reason unconditionally said "it will resume from the handoff when the limit resets", so the paused session promised the user an automatic continuation ("Jag fortsätter automatiskt från handoffen…") that was never scheduled. **Fix:** `pauseReason()` extracted to `core/resume.js`, driven by the actual arming outcome — armed ⇒ "Brink has scheduled an auto-resume shortly after the reset"; not armed (disabled / non-Windows / scheduler failure) ⇒ "auto-resume is NOT armed — tell the user this session must be resumed manually after the reset". brink.js also now treats a pre-existing `armed_*` flag as armed (a repeat pause in the same block used to skip arming and would have claimed "not armed" despite a live task). Tool-neutral wording (reason is shared by the claude + codex adapters). Tests: pure `pauseReason` cases + e2e assertion that a resume-disabled deny never promises a resume.

- **2026-07-06 — the 13:00 no-show (armed resume fired into the wrong project + failed silently).** First live ARMED pause (2 sessions in different projects, 10:00 and 10:45; both `armed_*` flags written, tasks registered). The task fired dead on time (13:01:34) — and errored: `claude.exe : No conversation found with session ID`. Root cause: `claude --resume <id>` is **project-scoped**, and the Proj passed to the task came from `hook.cwd`, which **drifts with mid-session shell `cd`s** (the session's Bash had cd'd into the brink repo, so HANDOFF.md and the resume both landed there while the transcript lives under the session's real project root). Worse: resume-once.ps1 logged the error, self-deleted its task, and notified nobody — the user discovered it by coming back to a dead session ("it's like i'm babysitting"). **Fixes:** (1) pause path now anchors on `CLAUDE_PROJECT_DIR` (hook env; probe-verified it stays on the session root while cwd drifts) for both HANDOFF.md and the resume Proj, falling back to hook.cwd; e2e test drift-vs-root added. (2) resume-once.ps1 checks the claude exit code and toasts the outcome BOTH ways — "auto-resume finished" / "auto-resume FAILED (exit N) - see .claude-resume.log" — which also delivers the resume-completion notification improvement. Live-fired: fake-sid resume errors → exit 1 → failure branch confirmed. ~~**Known-unknown:** resuming a session that is still OPEN in another window is untested `--resume` behavior~~ → **RESOLVED same day (live genrep, 2026-07-06 13:22):** full dress rehearsal with a REAL scheduler job against the fixed code — planted HANDOFF.md with a verifiable micro-task, armed via arm-resume.ps1 (Sid = an OPEN bridged session, Proj = CLAUDE_PROJECT_DIR root, Skip=1). Every link held: task fired on schedule → resume-once.ps1 → `claude --resume` resumed the OPEN session cleanly (forks; no conflict with the live window) → the fork read HANDOFF.md and DID the work (marker file created with exact content) → success toast fired → task self-deleted after the fork exited. One observer note: the claude fork runs synchronously inside resume-once.ps1, so cleanup happens minutes after fire time — a mid-run task-exists check is not a bug.

- **2026-07-06 — Notify simplified to desktop-only (owner decision).** Phone push (ntfy) removed entirely — owner never wanted it ("we don't need a phone push"); it was also the only outbound network call in the product, so its removal shrinks the trust surface to zero-network. notify.js now = desktop only, with a pure `desktopCommand()` builder: Windows toast (as before) + macOS `osascript display notification` + Linux `notify-send` — unit-tested cross-platform from any dev machine (tests/notify.test.js). Config key is now `notify.desktop` (default true); legacy `windows_toast: false` still honored on Windows. `brink doctor` updated (no phone-push line; accepts win-toast/mac-notify/linux-notify).

- **2026-07-08→10 — resume-in-place supersedes the headless fork (pivot + build).** The 2026-07-08 pause was reported as broken, but the scheduled resume had actually **succeeded** — it read HANDOFF.md and shipped a real commit at 23:56; the resume log lived in the session's own repo, not where the day-4 check looked. So the "3 failures" story collapsed to "2 real+fixed (07-05, 07-06) and one success." The genuine problem is UX, not reliability: headless `claude --resume -p` **forks a twin** that works invisibly while the user's live session stays frozen at the pause. **New design — resume-in-place (owner's idea):** on reset, inject `continue` into the LIVE paused session's terminal so it continues in place, visibly, instead of forking. **Feasibility proven by a standalone prototype:** `FreeConsole → AttachConsole(sessionPid) → CONIN$ → WriteConsoleInputW → FreeConsole` lands in the pane's console input buffer, which Claude's Ink TUI reads via raw-mode `ReadConsoleInputW` — works through Windows Terminal/ConPTY, per-pane precise (no wrong-tab problem), zero launch change. No supported local Claude API does this (Remote Control is cloud-driven; the SDK needs to have spawned the process), so OS injection is the right mechanism. Keystroke-faking (SendInput/WM_CHAR) was tested and **rejected** (can't target a background tab, corrupts live typing). **Load-bearing finding:** the submit Enter must be a **discrete** injection — a Return batched into the text burst is treated as a paste and does NOT submit; sequence is text (no Enter) → ~800 ms → lone Enter (proven against a real Claude session, Task 1 gate). **Architecture:** at pause, brink.js records the live session target (`Resolve-BrinkTarget` walks the hook's ancestry to the persistent `claude.exe`, skipping the ephemeral node hook) into `resume-ctx-<sid>.json`; at reset, `resume-dispatch.ps1` re-validates the pid is alive with the same start-time (PID-reuse guard), and either injects via `inject-continue.ps1` or falls back to the headless `resume-once.ps1` (dead/closed/non-Windows session). **Brink's own PreToolUse deny is the reset-verification gate** — an early nudge just gets re-denied, harmlessly, which dissolves the "did the limit actually clear?" problem. In-place is **Windows-only** in v1; the node-pty `brink run` wrapper and the UIA-gated keystroke tier are documented alternatives, not built. New config: `resume.in_place` (default true, win32-only) + `resume.continue_prompt`. Built over 9 TDD tasks on branch `resume-in-place` (fresh implementer + reviewer per task).

- **2026-08-19 — projection anchored to the sensor's clock, not the wall clock (defect + fix).** A 10-agent workflow fan-out took a 5h window 75% → 102% inside an 8-minute gap with no reading, on a 16/16-green install. Replaying the real `usage-history.jsonl` through this repo's own `projectedDecision()` found two defects behind one symptom. **(a) The headroom was too tight to get a vote:** the projection only wakes at `pause - headroom` = 81%, and the last live reading was 75% — the sweep put the cutoff at 18, so the incident sat one point under it. Default moved **12 → 20**. **(b) The rate decayed during the freeze — the real defect:** `span` was measured to `now` while `cur` stayed pinned at the reading's `updated_at`, so as a freeze continued the numerator stood still, the steep early samples slid out of `window_sec`, and the measured rate fell from 4.3/min (when the sensor froze) to 0.33/min five minutes later. At the *only* gate run we can prove happened — 11:33:50, evidenced by a `stale_` marker, which only a gate run writes — no legal headroom value would have paused. Fixed by measuring the rate over the **observed** interval (oldest sample → `updated_at`) and carrying it across the blind interval to estimate current usage (`estNow = cur + rate × blind`), judging headroom and the projection on that estimate. **Capped** by `projection.blind_cap_sec` (default 300 = `staleness.max_age_sec`): uncapped, a session that merely idled would pause on its first tool call because time had passed, which is exactly the "pause on age alone" the staleness guard deliberately refuses to do. A fresh or stampless reading takes the identical old path (`blind` = 0), so the existing suite passes unchanged. **(c)** Contradictory same-second history rows (26% and 73%, same session, same second — different rate-limit buckets in one log; ten such pairs in the file) could be picked as the rate baseline and manufacture a pause from noise; same-timestamp rows now collapse to their highest reading, since usage only climbs inside a window. **Also settled here:** the long-open sub-investigation from the 07-16 burn-in report — whether subagent tool calls traverse the user's PreToolUse hooks — is **yes**, including for background `Workflow()` fan-outs, proven by that mid-gap `stale_` marker written while the main session was idle. Subagents do not bypass the gate; the gate was reading a frozen number. **Known limit, accepted:** this extrapolates from a burn already visible when the reading froze, and does nothing for one that starts inside the gap; the statusline remains the only usage source and is still the structural fix (07-22 option #2, unbuilt). **Known gap, accepted for now:** `brink init` scaffolds every default into `config.json`, so existing installs keep their pinned `headroom: 12` and receive none of this until they edit it — including the machine the incident happened on.
